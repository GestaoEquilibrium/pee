## 1. Objetivo

Estabelecer o método único de elaboração, codificação, revisão, aprovação, publicação, distribuição e descarte de todos os documentos normativos do Grupo Equilibrium, garantindo que qualquer colaborador ou auditor consiga identificar, a qualquer momento, **qual é a versão vigente de um documento, quem a aprovou e quando**.

Este é o documento fundante do Sistema de Gestão da Qualidade. Nenhum outro documento normativo pode ser criado fora das regras aqui definidas.

## 2. Abrangência

Aplica-se a todas as unidades, setores e colaboradores do Grupo Equilibrium, incluindo estagiários e prestadores de serviço, e a todos os documentos normativos: manuais, POPs, fluxogramas, formulários, checklists e listas de controle.

**Não se aplica** a documentos assistenciais de paciente — prontuários, laudos, evoluções e termos assinados por paciente ou responsável —, que seguem regramento próprio de guarda e sigilo conforme a Resolução CFP nº 06/2019 e a Lei nº 13.709/2018 (LGPD).

## 3. Definições

| Termo | Definição |
|---|---|
| **Manual** | Documento amplo e conceitual. Descreve o *quê* e o *porquê*. Orienta, contextualiza e define diretrizes. |
| **POP** | Procedimento Operacional Padrão. Documento estreito e sequencial. Descreve o *como*, passo a passo, de forma auditável. |
| **Fluxograma** | Representação visual de um processo descrito em POP. Nunca substitui o POP; sempre o acompanha. |
| **Formulário** | Modelo em branco destinado a registro. Gera evidência quando preenchido. |
| **Registro** | Formulário preenchido. É a prova de que o procedimento foi executado. |
| **Lista Mestra** | Inventário único de todos os documentos normativos vigentes, com versão, responsável e data de revisão. |
| **Documento obsoleto** | Versão superada por outra. Permanece recuperável no histórico do repositório, mas não pode ser utilizada como referência operacional. |

## 4. Codificação

Todo documento normativo recebe código no formato:

```
PEE-[CADERNO]-[NNN]
```

### 4.1 Tipo

| Sigla | Tipo |
|---|---|
| `MAN` | Manual |
| `POP` | Procedimento Operacional Padrão |
| `FLX` | Fluxograma |
| `FOR` | Formulário |
| `CHK` | Checklist |
| `LIS` | Lista ou planilha de controle |
| `TER` | Termo com assinatura de terceiro |

### 4.2 Unidade

| Sigla | Unidade |
|---|---|
| `GRP` | Documento de aplicação a todo o Grupo |
| `EQ1` | Unidade 1 |
| `EQ2` | Unidade 2 |

> Documentos de aplicação geral usam `GRP`. A segmentação por unidade só é criada quando um procedimento é comprovadamente diferente entre unidades — duplicar documento idêntico entre unidades é proibido.

### 4.4 Numeração

Sequencial de três dígitos, por setor, a partir de `001`. Números **nunca são reaproveitados**: se um documento é descontinuado, seu número morre com ele.

Formulários vinculados a um POP herdam o código de origem com sufixo decimal:

```
POP-GRP-ABA-001        Registro de sessão ABA
FOR-GRP-ABA-001.1      Folha de registro ABC
FOR-GRP-ABA-001.2      Planilha de coleta por objetivo
```

Isso torna a rastreabilidade imediata em auditoria: dado um formulário, sabe-se o procedimento que o originou; dado um procedimento, sabe-se todo o registro que ele deve produzir.

### 4.5 Regularização do acervo existente

Documentos anteriores a este POP — incluindo os que hoje se chamam "POP 001" em mais de um setor — serão recodificados no momento da migração para o repositório, mantendo-se registro da denominação anterior no campo de histórico de cada documento.

## 5. Versionamento

| Situação | Efeito na versão |
|---|---|
| Correção de digitação, formatação ou link | Não altera versão |
| Ajuste de conteúdo que não muda a conduta | Incremento menor: 1.0 → 1.1 |
| Mudança de conduta, fluxo, responsável ou base legal | Incremento maior: 1.1 → 2.0 |

A versão vigente é sempre a que está na branch `main`. Não existe documento vigente fora de `main`.

## 6. Procedimento

### 6.1 Criação

1. Verificar na Lista Mestra se já existe documento cobrindo o tema. Sobreposição é motivo de recusa.
2. Reservar o código na Lista Mestra.
3. Criar branch nomeada `doc/[codigo-em-minusculas]` — exemplo: `doc/pop-grp-neu-001`.
4. Redigir a partir de `docs/4-controle/modelo-documento.md`, sem alterar a estrutura de seções.
5. Abrir pull request. O PR é o instrumento formal de submissão.

### 6.2 Revisão

O revisor verifica aderência ao modelo, correção técnica, coerência com documentos relacionados e adequação normativa. Aponta ajustes como comentários no PR. A revisão é registrada automaticamente pelo GitHub com autoria e data.

### 6.3 Aprovação e publicação

A aprovação é o merge em `main`, executado exclusivamente por quem detém o papel de Direção. O merge:

- publica o documento no site em até cinco minutos;
- registra data, hora e autor da aprovação de forma imutável;
- torna a versão anterior automaticamente obsoleta.

**Não existe aprovação verbal, por mensagem ou por e-mail.** Documento não mergeado não é documento vigente.

### 6.4 Segregação de funções

Quando a mesma pessoa acumular elaboração e aprovação, o acúmulo deve ser **declarado explicitamente** no cabeçalho do documento, com justificativa. Simular segregação inexistente é falha grave de auditoria; declarar o acúmulo é aceitável e verificável.

### 6.5 Revisão periódica

Todo documento tem data de revisão. A Lista Mestra sinaliza vencimentos com noventa dias de antecedência. Documento vencido é sinalizado como tal no site até que seja revisado — **a revisão vencida fica visível para toda a equipe**, o que impede a situação de documento expirado circulando como vigente.

### 6.6 Obsolescência

Não se apaga documento. A remoção do site retira a versão de circulação operacional; o histórico do repositório mantém o registro permanente para fins de auditoria retroativa.

## 7. Restrições de conteúdo

É **vedado** inserir no repositório, em qualquer arquivo ou histórico:

- dado identificável de paciente, incluindo nome, CPF, número de carteirinha, laudo, evolução ou imagem;
- credencial de acesso de qualquer natureza — senha, token, chave de API ou login nominal;
- documento pessoal de colaborador.

> **Motivo técnico:** o histórico do Git é permanente. Arquivo commitado por engano continua recuperável mesmo após remoção, e a correção exige reescrita do histórico. A verificação automática de segredos roda em todo commit e bloqueia a publicação quando detecta violação.

Credenciais de sistemas de operadora residem em cofre de senhas com acesso por função, nunca em documentação.
